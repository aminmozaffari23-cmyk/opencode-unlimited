## Gap #2 — the kill-switch and the tunnel ⇄ Psiphon transition

It took five distinct defects, each visible only on a root host with a real TUN device, to get a window that proves anything:

| # | What the run showed | The actual cause | Fix |
| --- | --- | --- | --- |
| 1 | `armed: guard_mode=None rules=0`, `ks_rc=1` | `install.sh --proxy` records `kill_switch:false`; a guard over an unpinned resolver refuses to arm, so the window measured nothing | `OUC_KILLSWITCH=1` re-opts a host in at runtime; the `OUC_DISABLE_KILL_SWITCH` veto still wins |
| 2 | every region "matched the host" (WARP's IPv6) | WARP's TUN was still up, so the tunnel core's own dial-outs left through WARP | take WARP's TUN down before probing, not after a success |
| 3 | every region "matched the host" (the bare IPv4) | `probe_egress()` probes **directly** in tunnel mode, never through the bridge — the controller was measuring itself and refusing itself as a leak | `probe_egress(proxy_url=…, strict=True)`; the candidate probe goes through the bridge |
| 4 | `psiphon@DE=-` and the core logs "shutdown by controller" | the tunnel-dialect guard blocks the Psiphon core's relays; only the supervisor switched dialect, and `ouc hop` did not | `_clear_warp_tun_for_psiphon()` performs the §2 handoff on the hop path too |
| 5 | `EAI_AGAIN opencode.ai`, then `ECONNREFUSED` from opencode | `warp-cli disconnect` took the resolver with the interface; and opencode was launched with **no** proxy in tunnel mode | `mode proxy` instead of `disconnect` (TUN gone, `warp-svc` DNS kept); `opencode_env()` follows the backend **and** the guard dialect |
